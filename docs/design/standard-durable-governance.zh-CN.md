# 治理审计、投递顺序与后台恢复

schema 15 在两个存储画像中加入导出/动态租约的 `lease_token`、`lease_until`，以及 outbox/sync 的组织事件顺序。升级在迁移事务内执行；原有组织、版本和密文保持不变。

## 本地事务边界

注册（含默认组织/项目/环境和 Refresh Token）、项目/环境/文件夹、本地机器身份、同步目标、Webhook、动态引擎配置、审计导出请求/重试及本地 TOTP 变更都将数据和审计一起提交。审计不可写时返回失败并回滚。敏感读取/下载先记录授权审计，再发送数据。数据库确认丢失返回未确认状态，普通治理客户端先刷新核对；秘密变更使用单独的幂等凭据与版本 CAS。

本地账号操作使用受信账号连接，且限定到当前认证用户；组织资源使用 runtime 角色与组织上下文。PostgreSQL 允许 owner 在当前组织内检查已验证的外部身份归属，以防止移除最后一个可用外部 owner。普通成员仍只可查询自己的外部身份行。

外部映射得到的 admin 不拥有新的凭据授权权力：身份连接、本地机器凭据、同步目标、Webhook、动态凭据管理等委托能力要求本地明确授予的 owner。原本地来源保留已有授权兼容性。项目/环境名称的可见性与秘密元数据授权分别检查，使 owner 能配置授权而不获得隐式 reveal。

更换绑定中的 issuer/Client 必须建立新连接并证明身份；既有绑定不能被修改配置重新解释。强制外部登录的组织，在停用/删除连接或更换账号身份时必须保留可通过启用连接登录的外部 owner；一次账号替换影响多个组织时也检查其余 owner 责任。

## 投递与顺序

业务事件在原事务中从组织审计锁分配递增顺序。审计 hash 链不要求该计数连续。outbox 确认与所有消费者任务落库仍属于同一事务。

一个同步目标采用单一有序流：较早的 pending 任务（包括正在退避的任务）阻止较晚版本；尚未物化的较早 outbox 也会阻止抢跑。目标可能把多个项目映射到同名下游 key，因此此约束比按秘密 ID 排序更严格。远端写入成功后，任务确认和审计事务提交；确认失败会再次投递同一快照，之后才允许新版本。

Webhook 使用稳定 Delivery ID，接收方仍需去重；不能声称跨网络 exactly-once。所有完成写入比较当前租约及截止时间；迟到 worker 不得确认新 worker 的任务。响应正文、SQL 中的密码和下游错误原文不进入任务错误字段或审计。

旧数据中缺少明确顺序的 outbox 被标记为需要人工重排的 dead 事件；不会假定秒级时间戳代表可靠的版本顺序。管理员检查死信后，通过目标「全量重推」生成当前状态的新快照。未具备资源快照的旧 sync 任务同样不能读取“最新值”冒充旧事件。上线迁移前应先清空旧队列或明确记录此重排步骤。

## 审计导出

worker 原子认领 pending 任务 60 秒，生成操作使用 45 秒数据库查询上限。每次认领写入独立的 0600 临时文件，完成并 fsync/close 后才将文件路径与完成审计提交。竞争者不会截断另一个 worker 的文件，崩溃后的任务在租约到期后可接管。

提交结果不确定时保留文件，因为数据库可能已引用它。运维清理只针对未被 `audit_exports.file_path` 引用、且超过最大租约窗口的孤立文件，并在备份后执行；不要直接删除整个 exports 目录。多实例部署必须共享 exports 的持久化目录，否则提供下载的实例可能找不到文件。导出文件只有审计元数据，不包含 Token 或秘密明文。

## 动态数据库租约

在外部 CREATE/ALTER 前，先持久化状态为 revoking 的恢复责任、加密密码和认领凭据，并记录请求审计。只有外部成功、本地机器身份仍有效、认领未过期且完成审计提交后，状态才变为 active。发生错误、进程退出或确认丢失，密码不下发，worker 会回收可能已创建的远端账号。

续期同样采用先持久化恢复责任、再远端更新、最后确认的顺序。失败的续期会进入回收，不保留无法确定的长效权限。手动回收先落库；暂时无法连接远端时返回 202/revoking。worker 60 秒认领、10 秒远端调用超时；失败 30 秒后重试，连续 5 次失败进入 failed，保留可见租约与人工重试入口，不丢弃回收责任。

实际外部效果仍是至少一次。PostgreSQL 回收操作必须幂等。公开测试使用独立的高权限目标数据库夹具创建、续期、删除角色；应用自身存储连接仍是 NOSUPERUSER/NOBYPASSRLS。
